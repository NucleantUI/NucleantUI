# Change detection: what SwiftUI does, what we do, what to change

Our study of how SwiftUI decides what to update (its dependency graph,
AttributeGraph, on macOS 26.7) set against how NucleantUI does it today.
NucleantUI already works much the same way in most respects. This lists
where it differs and what we can do about each difference.

## What SwiftUI does

1. **An equal write is no write.** Setting a value compares it with the old
   one first. If they are equal, nothing is marked and nothing updates.
2. **A real change only marks.** Everything downstream of the changed value
   is marked dirty. The walk stops at anything already dirty. Nothing is
   recomputed at that point: the host is told something under it is dirty,
   and the work happens on its next update.
3. **Only readers are marked.** Dirtiness follows dependency edges from the
   value to the things that read it. The view that *declared* the state
   isn't marked unless it read it too.
4. **Recomputing is lazy, inputs first.** A dirty value brings its inputs up
   to date first. Its rule (a view's `body`, say) runs again only if one of
   those inputs actually changed. Otherwise it is just marked clean.
5. **An unchanged result stops the cascade.** A rule that re-runs and produces
   a value equal to its last one doesn't mark anything downstream as changed.
6. **Dependencies are what the last run read.** Inputs a rule didn't read
   this time are dropped, so a `body` depends on what its taken branch read.
7. **"Equal" is structural, built once per type.** A type is broken into
   pieces once and the plan is cached: plain-data runs are compared as
   bytes, `Equatable` fields with `==` (depending on a per-type mode), enums
   by case and then payload, existentials by dynamic type and then contents,
   nested structs recursively, and class references and closures as heap
   objects (below).
8. **Closures are compared by what they captured** (to confirm with a probe,
   see step 3). A closure is a function pointer plus a captured context. The
   pointer is compared as bytes, and the context field by field like a
   struct. Two closures from the same spot that captured equal values are
   equal. One that captured a different value is not.
9. **Class references:** the same instance is equal. Different instances are
   unequal unless a field-by-field plan exists for that class; we haven't
   pinned down when that is.

## What NucleantUI does today

- **Writes** (`State/StateStore.swift`, `StateStorage.set`): every write bumps
  the version and dirties the *owner* plus every reader whose key-path chain
  overlaps the written one. The value isn't compared first.
- **Dirty set** (`Invalidator`): a set of view paths, consumed once per frame
  in `ViewHost.update()`. Same as (2): no work happens at write time.
- **Rebuild** (`ViewHost.rebuildScoped`): starts at each outermost dirty path
  and works down. Nothing above it re-runs.
- **Reuse** (`buildNode` in `Layout/ViewNode.swift`): a child is kept, and its
  `body` isn't run, when its identity, stack axis and lazy window match, the
  environment is equivalent, its inputs are equivalent (`_isEquivalent`), and
  nothing at or under its path is dirty. This is (4) and (5) in our own form.
- **Dependencies** are re-recorded on every build (`DependencyTracker`;
  `RebuildRecords.replace` drops the old reader registrations). Same as (6).
  We go finer than SwiftUI inside one state value: readers are kept per
  key-path chain, so a write to `[3].level` leaves the readers of
  `[2].level` alone.
- **Equivalence** (`Core/Equivalence.swift`, generated by `@View`): field by
  field. `Equatable` uses `==`, `ViewInput` uses `_isEquivalent`, a class is
  compared by identity, and anything else is *not equivalent*. Stored
  closures are skipped entirely, so they count as always equivalent.
- **Environment** (`EnvironmentValues._isEquivalent`): the whole environment
  is compared. One changed or uncomparable value (a closure, a class)
  anywhere makes every child "built under a different environment".
- **`@Observable`** (`State/Observation.swift`): `withObservationTracking`
  around each `body`. The first change dirties the path, and tracking is set
  up again by the next build.

## Side by side

| | SwiftUI | NucleantUI |
|---|---|---|
| Equal write | nothing happens | owner and readers rebuilt |
| Who is marked | readers only | owner always, plus readers |
| When work happens | next update | next frame ✓ |
| Body skipped when inputs equal | yes | yes ✓ |
| Dependencies | last run's reads | last build's reads ✓ (finer: per key path) |
| Non-`Equatable` plain value | compared structurally | never equivalent → rebuilt |
| Closure that captured a changed value | seen as changed | not seen; the **old closure keeps running** |
| Environment | per value that was read | the whole environment |
| Child with a dirty descendant | child kept, only the descendant runs | every view on the way down re-runs |

## What to change, in order

### 1. Skip equal `@State` writes

`StateStorage.set` compares the new value with the old one before bumping the
version or invalidating. If they're the same, it returns.

- How to compare: the same per-type comparator `Equivalence.swift` already
  caches (`Equatable` → `==`, class → identity, POD → bytes after step 2).
  Anything that can't be compared counts as changed, as it does today.
- Covers bindings too: `$x` and `$tracks[3].level` writes go through `set`.
- Keep `withAnimation` completions correct: a transaction whose writes were
  all no-ops must still complete. Check `noteTransaction` and
  `isClaimed`; a skipped write shouldn't leave a completion waiting.
- Find out what the toolchain's Observation does for an equal write to an
  `@Observable` property. That's outside our code, but it decides whether
  models get the same benefit.
- Tests (`ViewIdentityTests`): write the current value → zero builds
  (`PerfTrace.nodesBuilt`). Write through a binding chain → same. A
  `withAnimation` with only an equal write still runs its completion.

### 2. Plain-data fallback: compare POD values by bytes

Today a value that is neither `Equatable`, `ViewInput` nor a class is "not
equivalent", so a view holding a plain non-`Equatable` struct or enum rebuilds
every time its parent runs. SwiftUI compares plain data as bytes.

- In `_areEquivalent<T>` and `comparator(for:)`: if `_isPOD(T.self)`, compare
  with `withUnsafeBytes(of:)`. It's generic, uses no reflection, and works on
  every platform.
- Safe in the right direction: equal bytes mean the same values. Different
  bytes (padding, `-0.0` vs `0.0`) only cost a rebuild, as today.
- Non-POD values (holding a `String`, an array, a class) stay as they are:
  `Equatable` or not equivalent.
- Tests: a view with a non-`Equatable` POD struct input is reused when the
  parent re-runs with the same value, and rebuilt when it differs.

### 3. Closures: confirm, then compare by captures

This is a **correctness** issue today, not only a performance one. A view whose
only change is a closure is kept, and its *old* closure keeps running. The
`@View` docs already warn about it (`{ delete(userID) }` keeps the old
`userID`).

1. Confirm SwiftUI's behaviour with a public-API probe (macOS, in
   `research/SwiftUI-research`): a child holding `action: () -> Void` that
   captures a parent value. Count the child's `body` runs and record which
   value the action sees after the parent's value changes, then again with
   the value unchanged.
2. If confirmed, compare a closure conservatively: same function pointer and
   the same captured bytes → equivalent. Anything else → not equivalent,
   which rebuilds the view and so runs the new closure. Equal bytes are always
   safe, since same values and same references mean the same capture.
   Different bytes only cost a rebuild.
3. Open part: getting the size of a closure's captured context portably
   (macOS/iOS/Linux/Android). Decide whether it is reliable on every platform
   before switching the macro from "skip closures" to "compare closures".
   Until it is, a stale closure is still possible, and the docs stay as they
   are.
- Tests: a closure that captured a changed value runs the *new* value after
  the parent re-runs. A closure that captured the same value keeps the child
  reused.

### 4. Environment: depend on the values a view read

Today any environment difference rebuilds every child below a parent that
re-ran. SwiftUI only updates what read the changed value.

- Record environment reads per view, the way `DependencyTracker` records
  state reads. The `EnvironmentValues` subscript getter reports the key
  against the view being built. That covers `@Environment` properties and
  builtins that read the environment while making their node (a `Text`
  reading its font).
- The reuse check then compares only the keys that view (and what it built)
  read, instead of the whole `EnvironmentValues`.
- Care point: a builtin that reads the environment during *layout* rather than
  `makeNode` has to be recorded as well. Audit those first.
- Tests: change `.font` above two children, of which only one reads the font
  → one rebuilt, one reused.

### 5. Stop always dirtying the owner

`StateStorage.set` dirties the owner "as the safe floor", because some reads
happen outside `body` (a `ScrollView` reading its offset during layout).
SwiftUI marks readers only.

- Make those outside-`body` reads register like any other read, attributed to
  the view doing the layout (`RebuildRecords.addReads` already exists for
  `GeometryReader`).
- Then drop the owner floor. A view that declares state and only passes `$x`
  down no longer re-runs its own `body` when a child writes it.
- Do it after 1–4, with the audit of every layout-time read as part of the
  change.
- Tests: an owner that only passes `$value` to a child, child writes →
  owner reused, child rebuilt. `ScrollView` offset changes still re-layout.

### 6. Keep a child whose dirty state lies deeper

`buildNode` refuses to reuse a child when anything under it is dirty, so a
parent re-run rebuilds every view on the way down to the dirty one.

- Reuse the child when its own inputs are equivalent, and rebuild just the
  dirty descendants in the same frame, as `rebuildScoped` does for a dirty
  path whose ancestors didn't re-run.
- The trickiest of the six (ordering against `rebuildScoped`'s outermost-
  first pass and the shared `dirtyPaths`). Do it last, and only if traces show
  the intermediate re-runs matter.
- Tests: parent re-runs while a grandchild's state changed → child reused,
  grandchild rebuilt, final tree identical to a full rebuild.

## Staying as it is

- Key-path-chain readers: finer than SwiftUI already.
- Next-frame batching and one dirty set: same model.
- Dependencies re-recorded on every build: same model.

## Measuring

Every step is checked with `NUCLEANT_SWIFTUI_TRACE_PERF` (built/reused
counts) on an existing example before and after, plus its tests in
`Tests/NucleantUITests`.

## Progress (branch `change-detection`)

### Done

- **1. Equal `@State` writes** — `StateStorage.set` asks `_dynamicallyEquivalent`
  first and returns when the value is the same; nothing is bumped, nothing is
  dirtied. A `withAnimation` whose writes were all equal claims no frame and
  its completion runs on the next one (the same path as a body that wrote
  nothing). Bindings and `@FocusState` go through the same `set`; the host
  keeps a focus state in step with real focus, so an equal focus write has
  nothing to move.
- **`@Observable`**: the toolchain's macro (6.3.3) generates
  `shouldNotifyObservers` — `!=` for `Equatable`, `!==` for objects — so an
  equal write through a property's setter notifies nobody. An in-place
  mutation (`model.items[3].x = 5`, `+=`) goes through `_modify` and always
  notifies.
- **2. Plain data** — a value that is not `ViewInput`, not a class and not
  `Equatable` is compared by its bytes when it is plain data (`_isPOD`).
  Bytes are compared a word at a time, then the bytes left over. The same
  comparison is the fast path for plain `Equatable` values (equal bytes →
  equal, without calling `==`; different bytes still ask `==`) and for any
  plain value reaching the unconstrained `_areEquivalent`.
- **4. Environment per value read** —
  - `EnvironmentValues` stamps each value with the write that put it there;
    copies share stamps, so an inherited value needs no comparing.
  - Every read through the subscript is noted against the view being built
    (`EnvironmentReads`): `@Environment`s as they are bound, builtins in
    `makeNode` (a `Text` reading its font), everything below. Each record
    keeps the keys read anywhere in its subtree; a reused child adds its
    keys to its parent's.
  - Reuse compares only those keys (`agrees(with:on:)`).
  - A subtree kept under an environment that differs only in values it
    never read has its records **rebased**: each entry takes the new value
    of every changed key it inherited unchanged. Without that, a later
    rebuild started from one of those records (a scoped rebuild, a
    `GeometryReader` built during placement) would build with the old
    values. Rows of a `ForEach` share one computed difference.
  - Reads made after a record was filed — a scoped rebuild, a
    `GeometryReader`'s content during placement — are added to every record
    above (`addEnvironmentReads`), so a view that starts reading a value is
    not kept by an ancestor that never saw the read.
  - A `GeometryReader` rebuilding during placement takes its environment
    from its record, and a drag preview is built under the environment
    recorded at the source's path, not a copy kept when it was built.
  - Audit: the only code that builds views outside a `makeNode` is a
    `GeometryReader` during placement and a drag preview; both are covered.
    Dynamic colors resolve at draw time from the draw context, and every
    pass places every node again and compares its commands, so a kept
    subtree still repaints when the color scheme flips.
- **5. Owner floor dropped** — a write dirties the views that read the
  value, not the one that declared it. A read made while the host lays out
  or draws (`DependencyTracker.beginPlacement`), outside any `body`, has no
  view to record it against: a `ScrollView` placing at its offset, a lazy
  stack's window, a `PathShape` / `Canvas` closure reading state as it
  draws. Such a read flags the slot (`isReadDuringPlacement`), and a write
  to a flagged slot dirties the declaring view as before. Reads in event
  handlers flag nothing. A view that only hands `$value` down is no longer
  rebuilt when a child writes it.
- Steps 1, 2 and 4 confirmed: built, 379 tests green, and the tests that
  guard the rebase and the read propagation fail with either switched off.
  Step 5 likewise: the drawing-closure and scroll tests fail without the
  placement flag. Tasks and Moodboard build.
- **3. Closures compared by what they captured** — confirmed first with a
  public-API probe: SwiftUI skips a child whose closure captured equal
  values and re-runs it (with the new closure) when a capture changed.
  `@View` now generates `_areEquivalentClosures(self, other, \Self.x,
  name: "x")` for each stored closure (`Core/ClosureEquivalence.swift`):
  - Same function pointer, then the captures: the context's metadata gives
    the offset of the first capture and a capture descriptor listing each
    capture's type by mangled name; each is resolved by the runtime, found
    at its size and alignment, and compared as a view input. Worked out once
    per context kind. The same runtime layout on every platform.
  - The closure is read *in place*, at the property's offset in the view,
    looked up by name in the struct's own metadata (type descriptor field
    records + field offset vector). Handed over as a generic value — a key
    path's value included — a closure is wrapped in a thunk made at that
    spot, and two wraps of one closure don't compare.
  - Counts as changed (a rebuild, never a stale closure): generic captures
    (metadata sources), a captured `var` box, a captured closure (named by
    its lowered type), a non-`Equatable` struct holding a reference (SwiftUI
    compares those field by field; we don't), and a closure *value* handed to
    a generic-typed property (`() -> Content`), which gets wrapped. A closure
    literal written for a generic property is built for it directly and
    compares.
- Tests: `Tests/NucleantUITests/ChangeDetectionTests.swift`,
  `Tests/NucleantUITests/ClosureEquivalenceTests.swift`.

### Not started, and why

- **6. Keep a child whose dirty state lies deeper**: last, as planned.
